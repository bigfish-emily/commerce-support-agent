# 项目完整说明

核对日期：2026-09-26。本文解释当前实现及边界，配合 [完整架构图](ARCHITECTURE_DIAGRAMS.md)、[恢复与缓存协议](RECOVERY_PROTOCOL.md)、[使用手册](USER_MANUAL.md) 阅读。历史实验数据按各自协议保留，不代表当前代码重新跑出了同样结果。

## 1. 产品解决什么问题

这是公开历史订单数据上的订单助手与售后审核沙箱。消费者从自己的订单页进入，可以点按钮查询进度，也可以说“上周那件还没收到，能改地址吗，不行就申请退款”。后一类请求涉及订单指代、条件分支、缺失信息以及跨步骤处理，适合让语言模型组织请求；简单明确的操作保留原生按钮。

用户侧负责描述需求和补充信息；工作人员侧负责接手会话、核对证据、批准或驳回申请。审核完成后本地订单投影更新，用户页面轮询获取进度。没有真实退款到账或物流服务连接，也没有真实商家的流量收益验证。

工程价值集中在：从含糊请求形成受约束的计划，把不确定语言理解与可审计业务动作连接起来，并处理审核等待、重复提交、恢复与结果未知。功能清单本身不足以证明比成熟客服产品更有效。

## 2. 数据的来源和用途

- Olist：历史订单事实；全量加工口径为 98,666 条，仓库轻量演示种子为 518 条。该规模不等于真实线上客户数，也不等于本次评测样本数。
- 73 个类目画像：订单特征聚合，用于风险解释和内部排序；不应从某类目低分率推断单笔订单一定有问题。
- 本地 Policy Pack：明确标注的沙箱政策、FAQ、商家规则。它与 Olist 的真实公司政策没有同源保证。
- ResCommons 等客服语料：独立检索实验。客户、订单、标签与 Olist 不可直接关联；相似对话不能作为实际退款授权依据。
- SQLite：在历史事实之上保存本次沙箱申请、事件与订单投影。收到“退款申请”事件只表示申请状态发生变化。

## 3. 一句话如何走完系统

以“那件还没到，可以改地址吗，不行就退款”为例：

1. HTTP 层获取当前客户身份、订单上下文，先处理人工接手或已有待审申请。演示身份不能充当生产 IAM。
2. `plan_tasks` 生成任务计划。按钮携带结构化上下文；自由文本可进入快速判断、LLM planner 或失败降级。不能把所有请求都说成调用了 LLM。
3. `select_next_task` 按任务依赖和状态选择下一项，`extract_slots` 提取订单、动作等参数。订单不唯一或必要信息不全时需要澄清。
4. `retrieve_context` 查订单和政策；只读任务交给 `execute_read_task`，写意图交给 `build_after_sales_case`。
5. 节点内部形成规则决策和校验结果，选择自动处理、澄清、拒绝或等待审核。
6. 待审核走 `await_confirmation` 的 interrupt，返回当前请求。工作人员通过审核接口恢复图，进入 `finalize_escalation`；用户的 yes 不等于工作人员授权。
7. 执行前重新检查绑定，调用受治理工具，按成功、失败或结果未知记录任务状态，再选择下一任务。
8. `finalize_answer` 整理结果，HTTP 层处理客户表达与记录。最终答复只能陈述已查到的事实和已发生的状态变化。

这是十节点 StateGraph。新增 `execute_ready_reads` 在独立只读任务就绪时最多并发四项，每项使用私有 state，按计划顺序合并结果；单项查询沿原节点执行，写任务保持串行。Decision Engine、Verifier、ToolCallManager 是节点内部组件。条件句规划质量需通过真实 LLM 样本验证。

## 4. 三类判断的职责

### LLM：理解语言

输入为当前消息、可用上下文和结构化输出要求，输出候选意图、任务与槽位。槽位就是业务参数，例如订单指代、地址、退款原因。模型还可参与客户表达。语言理解可能错，因此候选计划不构成业务授权。

### Decision Engine：执行代码规则

输入包括动作、OrderStatusView、用户诉求及政策命中段落；输出 AfterSalesDecision，包含 outcome、allowed_actions、risk、requires_human、证据、政策引用、rule_id 和 policy_version。

规则检查订单是否发货、金额、延误与评价等。当前退款属于核查或申请流程，没有根据 LLM 判断直接划款。缺失的已退款、部分退款、优惠券支付、滥用信号为 null；不会伪装成已确认没有风险。

低风险自动门禁只覆盖部分动作。取消还要求明确的未退款与未部分退款证据，Olist 缺此字段时不能走该自动取消分支。改地址与普通建单使用各自门禁，尚不能称为所有未知事实均 fail-closed 的完整风控。

固定规则分值标注为 `legacy_heuristic`。它不是训练模型概率，不能解释为“82% 确定该退款”。规则版本标识可执行代码规则，不代表对全部政策文件做了版本一致性校验。

### Verifier 与执行绑定：检查不同问题

`verify_decision` 当前检查：
- outcome 要人工审核但 requires_human 为 false；
- 允许的写动作缺少政策引用；
- 来源明确为 model_calibrated 的低置信输出未采用安全退出；
- reject 却仍含允许动作。

它返回 passed、flags、required_next_step。它没有逐句证明检索政策适用性，也没有完成退款金额、退货窗口等所有业务校验。

`build_after_sales_case` 组合事实、决策和校验形成申请评估结果。`required_next_step` 是校验后的执行分流结果；planner 的 clarify 处理意图或指代不清，决策阶段的 clarify 处理读取订单和政策后才发现的证据缺失。例如“我要退款”意图明确，但是否需要退货凭证，要查询订单阶段与适用政策后才能知道。明确的必填信息仍应尽早在 extract_slots 检查。

额外的 execution_guard 将主体、会话、动作、决策与订单事实绑定。审核后重新读取订单，绑定缺失、参数变化、订单变化或规则版本变化则拒绝执行。这个检查能发现“审核的是 A，准备执行的却是 B”。它仍是本地执行前检查，接真实 OMS 还需要订单版本条件更新以避免检查后状态再变。

## 5. Redis、幂等和结果未知

“可选后端”指配置选择：默认单进程演示使用内存 RuntimeStore；设置 `RUNTIME_STORE_BACKEND=redis` 和 `REDIS_URL` 后才连接 Redis。不同进程需使用同一实例与命名空间，共享协调状态。内存后端不具备跨进程协调能力；Redis 故障不会自动切换内存继续执行写操作。

- 只读缓存采用 cache-aside：String 保存序列化 ToolCallResult，key 绑定租户、用户、角色、scope、订单授权集合、工具、参数和知识版本。命中直接返回，未命中查源并填充 TTL。仅缓存无错误的成功结果；缓存故障回源。订单状态、我的订单、写草稿和写工具不缓存。
- 政策 TTL 300 秒，内容 hash 参与 key，Markdown 更新后旧缓存不再命中；外部 MCP 政策暂不缓存，避免假设远端版本。类目画像和客服样例 300 秒，运营汇总 120 秒。
- 限流：Lua 原子执行 INCR、TTL 检查和 EXPIRE，使用固定窗口；同时修复历史无 TTL 的计数键。固定窗口仍可能出现边界突发，不等同于令牌桶。
- HITL 临时索引：JSON String + TTL，便于获取待审信息。TTL 删除键不等于自动恢复 LangGraph，也不等于取消外部支付。
- 副作用锁：SET NX EX，随机 token 为锁值，Lua 比较 token 后删除，避免旧持有者释放新锁。

订单写锁 key 来自 tenant + order_id，话术、地址或动作类型改变均不会产生同订单第二把锁。TTL 为 `max(int((timeout + backoff) * (retries + 1)) + 1, 3)` 秒，每 TTL/3 校验 token 后续租。丢失租约则结果标为未知；释放失败不覆盖业务结果。它负责短期协调，不能强制停止已派发线程或远端请求。

SQLite 业务幂等记录负责本地成功事件去重。另有 `write_attempts(operation_key PRIMARY KEY, status, evidence_ref, updated_at)`：按租户、订单先插入 submitted 占位，无自动到期，异常或超时保留 outcome_unknown。Redis 锁到期时，共享同一 SQLite 的新执行器仍不能越过该占位。成功后移除占位，成功去重由业务 case store 接续。尚未派发的锁竞争或 Redis 连接失败会释放占位。

跨存储采用持久化命令与执行凭据恢复：SQLite 业务记录为事实来源，checkpoint 保存执行位置，Redis 仅作缓存/协调。审核命令先落 `review_commands`，后台认领后恢复图，成功后标记 done；崩溃留下的命令到租约期后可重领。恢复发现本地 case 和订单事件已提交时读取原凭据，不重发写操作；业务申请缺失或审批绑定变化时拒绝执行，保留待核对状态。它提供可重放、失败关闭的恢复协议，不宣称三库原子事务或远端支付恰好一次。

FastAPI lifespan 启动扫描器，每 `REVIEW_SCAN_SECONDS`（默认15秒）读取 SQLite 到期申请并幂等登记超时命令，恢复 `Command(resume="__hitl_timeout__")`。审核截止时间默认 `HITL_TIMEOUT_SECONDS=900` 秒；Redis 键丢失不代表审批超时。服务停机期间无法发送通知，重启会补扫。缺失检查点等失败命令退避重试并保留错误；自动取消的是待审申请，不是直接取消订单或退款。

未知动作需要核对证据；内部 resolve 接口记录证据后才能解除隔离，当前没有自动查支付状态的对账任务。Redis 不可用不应解读为自动切换内存后继续安全写入；本实现也没有透明高可用保证。

外部支付成功、本地提交前崩溃的窗口仍需要下游幂等键、收据查询与对账。本地锁与 SQLite 唯一约束不能推出真实支付恰好一次。

## 6. RAG 到底怎么做

### 政策主链路

扫描 Markdown，按二级标题 `## ` 分段，保留来源文件、标题与正文。规则词表扩展 query，再计算：

`score = 3 * 标题交集词数 + 正文交集词数 / max(query词数, 1)`

先取 `max(k*4, 8)` 个候选，按 FAQ、merchant_rule、policy 等来源与请求的规则匹配加分；默认 k=3，因此候选为 12，再返回三段。这个 rerank 是规则加分，没有 cross-encoder。该路径没有训练型 embedding，也没有向量数据库参与政策召回。

结果用作回答依据与决策引用。命中标题仅证明检索到了段落，不能保证其适用于当前商品、商家和生效时间。这是后续政策检索与决策联动需要补强的地方。

### 独立客服语料检索

BM25 提供最多 100 个候选，HashingTextEmbedder 计算向量相似度；融合前分别保留最多 40 个排名结果：

`score = 0.2 / (20 + bm25_rank) + 2.0 / (20 + vector_rank)`

只累加该文档实际拥有的排名项。向量阶段也受词法候选限制，不能描述为两路完全独立的全库召回。

Hashing 向量由单词、bigram、char n-gram 特征生成；它没有 BGE 等模型的语义训练。LocalVectorStore 默认运行于本地进程；可选 Qdrant 保存与检索这些向量。更换存储后端不会自动升级 embedding。本路径未使用 LlamaIndex 或 Neo4j。

## 7. MCP 和后端怎么连接

客户主链路经过 ToolCallManager；默认本地 handlers。设置 `POLICY_TOOL_TRANSPORT=mcp_stdio` 可让实际政策检索调用独立 MCP 子进程，设置 mcp_http 可调用配置的 HTTPS 公共政策服务。client 先发现工具、检查 Schema，再调用并验证输出；stdio 路径已有实际集成测试。订单写入仍为本地服务，Stripe adapter 是独立组件。远程私有商家政策还需服务端主体授权契约，不能直接套用公共政策接入。

独立 server 的工具边界元数据描述 Schema、权限和风险。服务端仍须落实身份认证、授权、租户过滤与审计；不能依赖模型看到的描述保护数据库。

未来接现有电商后端时，BFF 负责可信身份和订单上下文，OMS/支付负责事实与持久化动作，Agent 组织交互与申请。退款收据、物流状态、到账时间均应来自相应系统；当前沙箱不具备这些外部连接。

## 8. 结果应该怎样解读

历史 24-case 对比记录为 7/24 与 22/24，分别为 29.17% 和 91.67%。但 baseline 与 workflow 工具面和治理不同，旧 scorer 还有顺序覆盖与措辞检查，这些样本已被检查和调试。因此只能作为探索性结果与回归材料，不能据此宣称架构因果提升或未见场景泛化能力。

ResCommons intent@k 表示前 k 个相似客服案例中是否命中意图标签。它不等于政策检索准确率、回答正确率或端到端任务成功率。历史 tau2 结果属于独立工具环境实验，不能代替 /customer/chat 评测。

CI 中离线回归验证程序约束，外部 benchmark launcher 为 dry-run。真实模型实验需要单独开启，记录模型、配置、数据哈希、逐行预测、工具结果、fallback、延迟与 token。规则通过不能当成真实 LLM 通过。

下一份可作为改进证据的实验应固定同一政策、身份、工具面、快照、历史消息和预算，以业务最终结果判分，允许不同合法路径；按场景家族划分开发与测试。分别报告任务完成、错误写入、审核分流、工具错误恢复、回答事实一致性和成本，再用消融分析组件贡献。详见 [评测协议与审计](EVALUATION.md)。

## 9. Jev 暂不可用如何处理

保持 `SEMANTIC_DECISION_SHADOW=off`，项目主链路不依赖 Jev。现有接口仅用于可选 shadow 分类：记录新消息是补充、修改、取消、新任务或含糊消息，不控制业务动作。Jev 当前无法申请访问，没有真实调用、延迟或准确率对比。

rules / llm 的相同 schema 可以保留用于后续实验。已有十条手写 smoke 只用于调通接口。shadow 本身会增加时延，未经过端到端验证不得宣称“System One 加速已落地”。详见 [执行完整性与分类实验](EXECUTION_INTEGRITY.md)。

## 10. 当前剩余边界

当前实现具备可演示的业务流程，但完整生产能力仍受以下限制：演示身份与本地状态存储、无真实下游对账、政策适用性检查有限、限流原子性与锁续租未补齐、规则风险事实不足、真实公平对比未完成。

架构图、功能接口和确定性回归可以证明实现存在；实际业务收益还要由对应业务数据与实验验证。本文不声明自动解决率、节省人工时间或真实用户满意度。
